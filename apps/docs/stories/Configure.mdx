# 📚 ETNOS Storybook

Bem-vindo à documentação visual do ETNOS. Este espaço existe para que a gente
consiga construir interfaces com mais consistência, mais velocidade e muito
menos retrabalho. ✨

O Storybook do projeto não é só uma vitrine de componentes. Ele é uma ferramenta
de trabalho do time para:

- 🎯 validar comportamento visual em isolamento
- 🧩 evoluir componentes da UI sem depender da aplicação inteira
- 🔍 revisar estados, variações e edge cases
- ♿ observar acessibilidade e legibilidade com mais clareza
- 🚀 acelerar desenvolvimento, QA e alinhamento entre produto, design e dev

## 💡 Por que isso é importante para a UI do projeto?

No ETNOS, a interface é uma parte central da experiência. A criança, a escola, o
responsável e o admin dependem de fluxos claros, acessíveis e consistentes.

Por isso, o Storybook funciona como uma espécie de **fonte visual de verdade**
da UI. Antes de pensar em tela pronta, fluxo integrado ou deploy, a gente pode
ver e evoluir cada peça isoladamente.

Isso ajuda muito a:

- ✅ padronizar componentes entre produtos e áreas do sistema
- ✅ evitar regressões visuais
- ✅ documentar estados importantes de cada componente
- ✅ facilitar onboarding de quem entra no projeto
- ✅ deixar decisões de UI mais explícitas para o time inteiro

## 🎮 Jogos no Storybook

Os jogos também fazem parte da experiência do produto, então eles merecem o
mesmo cuidado de documentação da UI tradicional.

Hoje, já temos no Storybook:

- 🧠 `MemoryGame`
- 🔎 `GuessGame`

### 🧠 MemoryGame

O `MemoryGame` está documentado com uma experiência isolada, o que permite:

- testar níveis e interações sem depender da aplicação inteira
- validar estados de pontuação, movimentos e acertos
- revisar comportamento visual das cartas e cobertura
- evoluir a UX do jogo com mais segurança

### 🔎 GuessGame

O `GuessGame` agora também roda bem no Storybook com uma experiência isolada.
Isso é importante porque ele passou a depender de conteúdo vindo do banco e de
validação no backend, então a story funciona como um ambiente controlado para:

- visualizar o layout completo do jogo
- testar fluxo de dicas, letras e verificação da palavra
- validar o estado final com descrição da resposta
- revisar a UI sem depender de autenticação ou API real

Esse tipo de isolamento é muito valioso para jogos, porque comportamento visual
e interação normalmente mudam bastante ao longo da evolução do produto. 🎯

## 🧬 Organização por Atomic Design

A UI segue a lógica de Atomic Design para facilitar composição e manutenção:

1. **Átomos** ⚪  
   Componentes básicos, como botões, cards simples e elementos essenciais.

2. **Moléculas** 🟡  
   Combinações pequenas de átomos com uma responsabilidade clara.

3. **Organismos** 🟠  
   Blocos maiores, normalmente com mais regras visuais e funcionais.

4. **Templates** 🔵  
   Estruturas de página que organizam regiões e composição.

5. **Experiências / Fluxos** 🟣  
   No caso dos jogos, temos experiências completas que simulam a interação real.

## ✍️ Como adicionar um novo componente

Fluxo recomendado:

1. Crie ou ajuste o componente no pacote ou app correto.
2. Crie uma story próxima do componente, preferencialmente no mesmo diretório.
3. Documente pelo menos o estado principal e os estados críticos.
4. Se houver comportamento complexo, crie uma story interativa.
5. Se fizer sentido, complemente com MDX para contexto adicional.

Exemplo de story básica:

```tsx
import type { Meta, StoryObj } from '@storybook/react-vite';
import { MeuComponente } from './MeuComponente';

const meta = {
	title: 'Atoms/MeuComponente',
	component: MeuComponente,
	tags: ['autodocs'],
} satisfies Meta<typeof MeuComponente>;

export default meta;

type Story = StoryObj<typeof meta>;

export const Default: Story = {
	args: {
		// props do componente
	},
};
```

## ✅ Boas práticas para stories

- 🧩 prefira stories pequenas, objetivas e úteis
- 🎛️ exponha props que ajudem a testar variações reais
- 📚 documente estados vazios, loading, erro e sucesso quando fizer sentido
- 🎮 para jogos e fluxos complexos, prefira experiências isoladas
- 🧪 use stories para facilitar teste manual e revisão visual
- ♿ observe contraste, leitura, foco e área clicável

## 🕹️ Padrão recomendado para jogos

Para jogos, o padrão ideal no ETNOS é separar:

- um **container**, responsável por hooks, query, autenticação e integração
- uma **experience**, responsável por renderização e interação local

Esse formato traz várias vantagens:

- facilita o Storybook
- reduz acoplamento com backend
- simplifica testes
- melhora reuso
- deixa a UI mais previsível

## 🔍 O que revisar antes de subir uma mudança de UI?

Checklist rápido:

- 🎨 o componente respeita o visual esperado?
- 📱 funciona bem em resoluções menores?
- 🧠 os estados importantes estão cobertos na story?
- ♿ a interface continua acessível?
- 🧪 existe teste cobrindo o comportamento principal?
- 📚 a documentação do Storybook ajuda alguém novo a entender o componente?
